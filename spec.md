# Pharmacy Ordering System: Implementation Spec

> **Source of truth: [`base-spec.md`](base-spec.md).** This document is an elaboration of the
> original challenge, written to guide the build. It is deliberately narrower and more concrete,
> but where it diverges from `base-spec.md`, `base-spec.md` wins. Assumptions invented here (the
> prescription format, ticket numbers instead of names, roles, the live board) are marked as
> assumptions, not requirements.

Spec for a coding agent. Build the project from this document. It records decisions already made; do not re-open them. Scope is time-boxed to roughly five hours (section 15); section 17 lists what is deliberately out of scope.

## 0. How to work

- Work milestone by milestone (section 15). After each milestone: run the app and the tests, fix failures, commit with a clear message, then continue.
- **Keep it simple.** Readable, explicit, boring code. No unnecessary abstractions, no reflection tricks, no framework features that need a paragraph to explain. Aim for small files (roughly under 150 lines each). Comments explain why, not what.
- The author will be interviewed on every line, so prefer code that is easy to walk through.
- Do not add features beyond this spec. Non-goals are listed in section 17.
- If something in this spec conflicts with reality (an extension attribute name, a Dev Services quirk), pick the simplest option that works and record it under a **Deviations** heading in `DESIGN.md`. Never silently change a decision.
- Verify extension names and configuration attributes against current Quarkus documentation. Do not rely on memory for them.

## 1. Objective

A prescription fulfillment system for a pharmacy (take-home tech challenge).

Flow: a patient enters a prescription number at a kiosk, receives a ticket number, and watches a live status board. The backend checks and reserves stock, routes the order to a pharmacist approval queue, then a packaging queue, then a delivery queue. A pharmacist takes the order from the delivery queue, calls out the ticket number, and hands the medication over.

Priorities, in order:
1. **Patient experience:** simple kiosk, clear live board, plain-language failure states.
2. **Simplicity:** no over-engineering.
3. **System design:** clear components and coordination.
4. **Failure handling:** partial failures handled and visible (section 10).

Pharmacist and packager interfaces may be plain.

## 2. Hard requirements

- Kotlin and RabbitMQ are mandatory.
- A public Git repo with clear run instructions, documented system design and technology decisions, and notes on what would be done next.
- Runs with as little setup as possible: JDK and Docker only.

## 4. Assumptions (decided)

- Input is a **prescription number**, decoded locally (section 11): one digit per medication id, starting at id 1. `P-10000` means 1 of medication 1; `P-12000` means 1 of medication 1 and 2 of medication 2; a sixth digit addresses the added "favorite" medication. base-spec does not define a format, so this is our assumption.
- The prescription source is external and sits behind a `PrescriptionClient` interface. The shipped implementation is fake and derived from the number, so it never performs I/O.
- Multiple pharmacists. Each works one order at a time. A pharmacist picks a role for the session: approvals, deliveries, or both.
- The packager is a separate concern, simulated by a consumer in the same app.
- Ticket number = order id, from a DB sequence starting at 100. It is what patients see and pharmacists call out.
- No patient accounts or login. No authentication for pharmacist screens.
- The public board shows **ticket numbers only**, never names or medications (privacy). base-spec says the pharmacist calls out the patient's number or name; we call the ticket number instead, so no personal data is ever displayed.
- Orders are all-or-nothing. No partial fulfillment.
- Intake is synchronous: the kiosk request reserves stock, creates the order, and returns the ticket.

## 5. Order lifecycle

Statuses: `OUT_OF_STOCK`, `AWAITING_APPROVAL`, `IN_REVIEW`, `REJECTED`, `PACKAGING`, `READY`, `COMPLETED`, `FAILED`.

Terminal statuses: `COMPLETED`, `REJECTED`, `OUT_OF_STOCK`, `FAILED`.

**Every transition is a conditional update** (`UPDATE orders SET ... WHERE id = :id AND status = :expected`). If it affects 0 rows, the transition is a no-op (the message is a duplicate or the order already moved). This makes at-least-once delivery safe.

| # | From | To | Trigger | Effects (same DB transaction unless noted) |
|---|---|---|---|---|
| 1 | none | `AWAITING_APPROVAL` | Kiosk submit, all items reserved | Insert order and items; reserve stock. After commit: status event |
| 2 | none | `OUT_OF_STOCK` | Kiosk submit, any item cannot be reserved | Nothing stays reserved (all-or-nothing). Status event |
| 3 | `AWAITING_APPROVAL` | `IN_REVIEW` | Pharmacist "Take next" (approvals) | Takes a write lock so two pharmacists cannot claim the same order |
| 4 | `IN_REVIEW` | `PACKAGING` | Pharmacist approves | After commit: publish to `orders.packaging` and a status event |
| 5 | `IN_REVIEW` | `REJECTED` | Pharmacist rejects | **Release stock** (guarded, once) |
| 6 | `PACKAGING` | `READY` | Packager finishes | Status event |
| 7 | `PACKAGING` | `FAILED` | Dead-letter handler (packager rejected the message) | **Release stock** (guarded, once). Status event |
| 8 | `READY` | `READY` (taken) | Pharmacist "Take next" (deliveries) | Write lock; status stays `READY` |
| 9 | `READY` | `READY` (called) | "Call patient" | Set `called_at`. Status event |
| 10 | `READY` | `COMPLETED` | "Handed over" | **Consume stock** |
| 11 | `OUT_OF_STOCK`, `REJECTED`, `FAILED` | dismissed | Pharmacist "Resolved" | Set `dismissed_at`. Board hides the ticket |

**Stock effects** (each a single conditional statement per medication):
- Reserve: `UPDATE medications SET reserved = reserved + :n WHERE id = :id AND stock - reserved >= :n`. Zero rows means shortage.
- Release: `SET reserved = reserved - :n`, only if the order's `stock_released = false`; set the flag in the same transaction.
- Consume: `SET stock = stock - :n, reserved = reserved - :n`, only as part of transition 10.

**Reservation is all-or-nothing:** process items in a fixed order (by medication id) to avoid deadlocks. On any shortage, roll the reservation transaction back, then create the `OUT_OF_STOCK` order in a second transaction. A prescription containing a medication missing from the catalog counts as out of stock.

## 6. Data model

Schema is generated by Hibernate; the seed lives in `src/main/resources/import.sql`.

**`orders`**: `id` (ticket, sequence starting 100), `prescription_code`, `status`, `status_changed_at`, `called_at` (nullable), `dismissed_at` (nullable), `stock_released`.
One `orders` row per ticket. There is no `claimed_by`: a taken order is identified only by being locked during the claim transaction (see section 8).

**`medications`**: `id`, `name`, `stock`, `reserved`, with `reserved >= 0 AND reserved <= stock`.

**`order_items`**: `order_id`, `medication_id`, `amount` (> 0), primary key `(order_id, medication_id)`.

Seed medications (`stock`): Amoxicillin (Antibiotic) 5, Ibuprofen (Pain Relief) 10, Lisinopril (Blood Pressure) 15, Metformin (Diabetes) 20, Atorvastatin (Cholesterol) 25, and one "favorite" — Methylphenidate (ADHD) 30. The first five come from `base-spec.md`; the last satisfies its invitation to add a favorite medication.

The duplicate-submit guard (one active order per prescription code) is a best-effort query in the intake path, not a database partial index: Hibernate schema generation cannot express one. Record this limitation in `DESIGN.md`.

Optional if time allows: an `order_events(order_id, from_status, to_status, at, actor)` audit table. Not required.

## 7. Messaging topology

Declare topology at startup, explicitly and idempotently. Payloads are tiny JSON. The DB is the source of truth, so consumers load the order by id.

| Object | Type | Notes |
|---|---|---|
| `orders.packaging` | durable queue | Rejected messages are dead-lettered to `orders.dlx` with routing key `packaging.failed`. Payload `{"orderId":123}` |
| `orders.dlx` | direct exchange | Routes `packaging.failed` to `orders.packaging.dlq` |
| `orders.packaging.dlq` | durable queue | Consumed by the dead-letter handler |
| `orders.status` | fanout exchange, durable | Payload `{"orderId":123,"status":"PACKAGING"}` |
| one status queue per app instance | exclusive, auto-delete, server-named | Bound to `orders.status`; feeds the SSE broadcast |

Rules:
- Publish **after** the DB transaction commits. If a publish fails, log it. There is no republish/sweeper: a lost event only makes the board wait for its next poll. This limitation is recorded in `DESIGN.md` and section 17.
- The packager rejects a message it cannot process; the connector routes rejected messages to the DLX/DLQ. There is no broker-level retry counter (see `DESIGN.md`).
- Pharmacist "Take next" claims in the database (section 8). There is no long-held unacked message.

## 8. Components

**Intake.** `OrderService.create`: validate the format, decode the number, reserve all items, insert the order and items, or create the `OUT_OF_STOCK` order. Signal the failure cases in section 10 (malformed, duplicate active order, source outage).

**Pharmacist service.** `OrderService` plus `PharmacistResource`.
- *Take next:* the role decides the queue. If both roles, take delivery (`READY`) first, then approvals. The claim locks the oldest matching order with a write lock and, for approvals, moves it to `IN_REVIEW`; for delivery the status stays `READY`. A delivery claim that is already taken is identified only by the in-flight lock, so "take next" cannot return an order another claim transaction is holding.
- *Approve / Reject / Call patient / Handed over / Resolved:* the transitions in section 5. Reject takes no reason.

**Dead-letter handler.** Consumes `orders.packaging.dlq`, runs transition 7 (`PACKAGING` → `FAILED`, release stock, status event).

**Packager consumer.** `@Incoming` on `orders.packaging`, blocking, one message at a time. If the order is not `PACKAGING`, ack and skip. Sleep a random delay (default 3 to 8 seconds, 0 in tests). If the prescription code is the demo failure code, throw; the connector rejects the message, which dead-letters it to the DLQ. On success run transition 6.

**Status publisher.** A single method used by every transition to publish to `orders.status`.

**Status stream (SSE).** Each instance consumes its own status queue and pushes into a broadcast processor, which fans out to that instance's SSE clients. `GET /board/events` returns an SSE stream where each event is named `changed` with dummy data (no HTML travels over SSE). Emit a heartbeat event (named `ping`) every 15 seconds.

## 9. Screens and routes

All server-rendered (Qute plus htmx), Pico.css, no login. Use `@CheckedTemplate`. One shared `base` template.

**Kiosk `/`.** One field for the code, native validation via the `pattern` attribute, server-side re-validation.
- Success shows "Your number is N. Watch the board. We will call you." and resets itself after 10 seconds (htmx `load delay:10s`).
- Out-of-stock orders still get a ticket with "Please see the pharmacist at the counter."
- Errors re-render the form with the message and keep what was typed. Always answer HTTP 200 (htmx does not swap 4xx and 5xx).
- Beware: Qute reads `{` followed by a non-space as an expression. Never put `{n,m}` in a template.

**Status board `/board`.** For wall-mounted screens. `data-theme="dark"`, very large type, three columns.
- `GET /board/columns` returns the three columns rendered fresh from the DB.
- **Preparing:** tickets in `AWAITING_APPROVAL`, `IN_REVIEW` (stage "Pharmacist review") and `PACKAGING` (stage "Packing"). A ticket unchanged for longer than `pharmacy.board.delayed-after` shows "taking longer than usual".
- **Ready:** `READY` tickets. A ticket with `called_at` within the last 60 seconds is highlighted ("Now calling").
- **See pharmacist:** `OUT_OF_STOCK`, `REJECTED`, `FAILED` that are not dismissed.
- `COMPLETED` and dismissed tickets are not shown. Ticket numbers only.
- `hx-ext="sse" sse-connect="/board/events"` with `#columns` triggered by `load, sse:changed throttle:500ms, every 30s`. A reload or dropped connection must always recover the correct state.

**Pharmacist `/pharmacist`.** Plain, functional.
- A role selector (Approvals / Deliveries / Both). The role travels as a query parameter; no session or cookies.
- Console (refreshes every 5 seconds): current order card with the actions for its stage, a "Take next" button, counts of waiting orders per queue, and a "Needs attention" list (`OUT_OF_STOCK`, `REJECTED`, `FAILED`, not dismissed) with a "Resolved" button.
- Endpoints: `POST /take`, `/approve/{id}`, `/reject/{id}`, `/call/{id}`, `/handover/{id}`, `/dismiss/{id}`. Each returns the console fragment. If a conditional update loses a race, show "That order changed. Take the next one."

There is no packager UI.

## 10. Failure handling

| Failure | Behavior | Where it surfaces |
|---|---|---|
| Malformed code | Rejected before any write | Kiosk message |
| Prescription source down | Error logged, nothing created | Kiosk "Something went wrong. Please ask at the counter." |
| Duplicate submit for an active prescription | Best-effort check, nothing created | Kiosk "already being prepared" |
| Medication out of stock | `OUT_OF_STOCK` order, all-or-nothing | Kiosk sends patient to the pharmacist; board "See pharmacist" |
| Two orders race for the last box | Atomic conditional reserve; exactly one wins | Board |
| Rejected or failed order | Stock released once, guarded by `stock_released`, in the same transaction as the status change | Board |
| Packager throws | The connector rejects the message onto the DLQ, then `FAILED`, stock released | Board "See pharmacist"; log |
| Message delivered twice | Conditional transitions make it a no-op | — |
| Publish fails after commit | Logged; the order stalls and appears as delayed | Board "taking longer than usual"; limitation noted in `DESIGN.md` |
| SSE drops | Browser reconnects; the board also polls every 30 seconds | Board recovers |

## 11. Prescriptions and demo triggers

Decode after trim/uppercase: `^P-([0-9])([0-9])([0-9])([0-9])([0-9])([0-9])?$` — five digits for medication ids 1–5, plus an optional sixth for the added favorite. Digit position *i* (1-based) is the quantity of medication id *i*; zero digits are dropped. An empty or malformed number is rejected.

Besides ordinary numbers, a few codes exist only to demonstrate failure handling. Document them in the README as demo-only hooks.
- `P-60000`: asks for 6 of medication 1, which has 5 on hand → `OUT_OF_STOCK`.
- `P-00009`: a valid order whose packaging always throws → dead-lettered to `FAILED`, with stock released.
- `P-99999`: the prescription lookup throws → prescription service outage message.
- `P-000001` (six digits): one of the added favorite medication.

## 14. Tests

Use `@QuarkusTest` with Dev Services. Keep it to these:
1. **Intake validation (unit):** trimming, uppercase normalization, malformed code, source-down code.
2. **Last-box race:** one medication with `stock = 1`, ten parallel submits, exactly one order created, nine `OUT_OF_STOCK`, `reserved = 1`.
3. **All-or-nothing:** order with two medications where the second is short leaves the first's `reserved` unchanged.
4. **Happy path end to end:** submit, take (approvals), approve, wait for `READY`, take (deliveries), call, hand over. `stock` decreased by the ordered amounts and `reserved` back to 0.
5. **Idempotency:** approving twice, or releasing twice, changes state once.
6. **Packager failure:** the demo failure code ends in `FAILED` with stock released.

## 17. Non-goals

Authentication, partial fulfillment, transactional outbox, per-patient phone tracking page or QR, async intake, metrics and alerting, running multiple app instances in practice (the design supports it, and no test is required), a sweeper/republish job, Flyway migrations, and RabbitMQ `basic.get`-style pull.

What we would do next, with more time: a transactional outbox or a small scheduled republisher to recover from a failed publish after commit; Flyway migrations for real deployments; a stale-claim sweeper; an audit table.
